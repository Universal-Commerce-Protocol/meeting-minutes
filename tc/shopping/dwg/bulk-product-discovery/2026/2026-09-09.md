## 2. Technical Discussions & Working Group Consensus

- **Topic:** P0 scope - endpoint security and feed URL delegation
  - **Discussion:** Zhaocheng Li defined the P0 scope as endpoint security and URL delegation. A business advertises where its feed lives, and the protocol accommodates either returning feed content directly through a proxy endpoint or returning a URL that points at externally hosted storage such as S3 or a CDN.
  - **Working Group Position:** Recorded as the proposed P0. Final P0 versus P1 assignment remains open - see section 3.

- **Topic:** P1 scope - feed quality safeguard
  - **Discussion:** Zhaocheng Li proposed a P1 quality safeguard: a feed process should fail if more than 5% of records cannot be parsed. The group discussed pairing a threshold of this kind with diagnostic and error reporting so that a business learns which records were defective, while cautioning against over-engineering the reporting path in a first version.
  - **Working Group Position:** Recorded as a P1 candidate. Neither the threshold value nor the reporting mechanism is settled.

- **Topic:** Diagnostics and feedback to businesses
  - **Discussion:** Ilya Grigorik proposed reusing a generic feedback API or the existing `messages` mechanism to return structured error payloads, rather than inventing a feed-specific channel. Jason Mathnov suggested a lower-complexity starting point: publish a contact email in the well-known configuration file so a platform has somewhere to report problems. Reid Kairalla noted that diagnostics should not be limited to parse errors and should also carry broader status, such as whether a product is actually available on a given sales channel.
  - **Working Group Position:** No decision. Three candidate mechanisms are on the table - structured payloads over the existing `messages` mechanism, a generic feedback API, and a contact address in the well-known profile.

- **Topic:** Asynchronous delivery and feed orchestration
  - **Discussion:** Reid Kairalla proposed an optional asynchronous delivery mode in which a platform can trigger catalog generation, improving freshness relative to a fixed publication schedule. Ilya Grigorik cautioned that a dynamic request API for batch generation introduces significant implementation complexity for businesses and opens a potential avenue for abuse.
  - **Working Group Position:** Consensus to treat ad-hoc dynamic feed requests as a potential future feature rather than a baseline requirement.

- **Topic:** Declaring alternative feed sources
  - **Discussion:** Reid Kairalla suggested allowing businesses to declare alternative sources for catalog data - for example an existing Merchant Center feed - so that platforms could reuse what a business already publishes. Ilya Grigorik questioned the necessity of advertising alternative sources within UCP, noting that platforms holding those integrations can already rely on them directly.
  - **Working Group Position:** Deferred. The group agreed to hold the decision on supporting non-UCP feed formats pending investigation of the interoperability risks.

- **Topic:** Architecture - static handshake, dynamic manifest
  - **Discussion:** Ilya Grigorik proposed using the existing static well-known files for the handshake and introducing a new dynamic endpoint for feed manifests, so that feed access leverages UCP's existing authentication rather than defining a parallel scheme. Vinod Kumar confirmed the design alignment.
  - **Working Group Position:** Alignment on the split between a static well-known handshake and a dynamic manifest endpoint. Placement of the endpoint intersects the Shopping TC's services-versus-capabilities discussion - see section 3.

- **Topic:** Milestone roadmap
  - **Discussion:** Ilya Grigorik outlined a phased roadmap: (1) discovery and contextual feeds, (2) delta feeds, (3) push updates. He recommended treating feed delta updates and push mechanisms as discrete, composable capabilities, and decomposing them so that each phase delivers material value incrementally rather than landing as a single large change. Vinod Kumar confirmed that the phased milestone approach meets the group's current goals.
  - **Working Group Position:** Consensus on the three-phase roadmap and on decomposing delta and push into separately deliverable capabilities.

- **Topic:** First-phase scope and the next release
  - **Discussion:** Vinod Kumar proposed finalizing the first-phase ("crawl") strategy for the next release by the end of the week. The group planned to reconcile the diagrams in the "Problem and Scope" tab of the working document in order to identify decisions that are coupled to one another.
  - **Working Group Position:** Target end of week for a finalized first-phase strategy - see section 5.

- **Topic:** Documentation and review timeline
  - **Discussion:** Ilya Grigorik committed to consolidating the presentation sketches from this session into the "Problem and Scope" document. James Andersen asked the group to leave review comments by Friday 2026-09-11 so that the feedback can be carried into the upcoming Shopping Tech Council meeting.
