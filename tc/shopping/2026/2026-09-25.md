## 2. Open Discussions & PR Reviews

- **Topic:** Saved Fulfillment Destination Selection and Account Linking Boundaries
  - **Notes:** Greg Smith introduced PR 735, which proposed sharing user address book records back to the platform, highlighting security and privacy tensions around exposing sensitive buyer data when operations are not explicitly gated at appropriate access levels. Amit Handa noted the protocol provides communication pipes while leaving data-sharing policies to the merchant, though clear privacy boundaries are needed.
  - **Discussion:** Drew Olson noted that payment handlers already provide destination and address selection during express checkouts, meaning multiple mechanisms currently exist. James Andersen highlighted that PR 585 previously documented business-populated response values under identity linking, but questioned data protection boundaries if platforms ingest user address books outside checkout flows.
  - **Decision:** The group deferred final commitment on the get account and identity linking proposal pending a scheduled follow-up deep dive.
  - **Context:** [docs: clarify saved fulfillment destination selection](https://github.com/Universal-Commerce-Protocol/ucp/pull/735), [docs: clarify business-populated response values for identity-linked sessions](https://github.com/Universal-Commerce-Protocol/ucp/pull/585)
- **Topic:** Get Account Primitive and Authenticated Vault Access
  - **Notes:** Ilya Grigorik proposed introducing a formal `get account` primitive to UCP, reflecting Shopify's production pattern where an authenticated OAuth bearer token unlocks access to vaulted customer addresses, preferences, and order history, automatically populating subsequent carts and checkouts.
  - **Discussion:** Amit Handa and Drew Olson discussed how `get account` interacts with embedded platform identities and existing buyer representations in cart and checkout responses. The council agreed to dedicate Monday's deep dive session to resolving the authorization model and identity linking boundaries.
- **Topic:** Media Variants and HTTPS Enforcement
  - **Notes:** Ilya Grigorik presented updates to PR 690 modeling image, video, and 3D variants, noting that strict HTTPS enforcement was relaxed to a platform refusal model to preserve backward compatibility with version 0825. Under the updated specification, platforms may refuse to load media assets not served over HTTPS.
  - **Discussion:** Amit Handa and Drew Olson agreed with the platform refusal approach, noting that while strict HTTPS is standard for browser runtimes and mitigates script injection risks, platforms routinely enforce subjective transport and validation requirements without requiring breaking schema changes across the protocol.
  - **Decision:** The participants aligned on updating the media PR to allow platform refusal of non-HTTPS resources without a breaking schema change.
  - **Context:** [feat(media): model image, video, external video, and 3D variants](https://github.com/Universal-Commerce-Protocol/ucp/pull/690)
- **Topic:** Ask Capability Proposal and Extensible UI Representation
  - **Notes:** Ilya Grigorik presented PR 538 for the `ask` capability, confirming the operation has zero stateful side effects and does not execute downstream commerce operations. To support rich presentation, the specification defines an extensible response structure providing `text/plain` fallback alongside optional rich representations, including an Agent-to-User Interface (A2UI) extension for interactive component rendering.
  - **Discussion:** Amit Handa commended the component-based A2UI integration as safe and elegant because it avoids arbitrary HTML execution, suggesting similar UI representations could eventually extend other UCP responses. Ilya Grigorik explained that extending base description objects allows A2UI to slot cleanly into any UCP capability via standard protocol negotiation.
  - **Decision:** The group deferred final alignment on the Ask proposal to a dedicated Monday deep dive session.
  - **Context:** [feat: `ask` capability for natural-language Q&A](https://github.com/Universal-Commerce-Protocol/ucp/pull/538)
- **Topic:** Architectural Boundaries: Structured UCP Protocols vs. Browser Actuation
  - **Notes:** Drew Olson raised an architectural question regarding the division of labor between structured UCP interactions and emerging agent paradigms such as browser actuation or WebMCP. Ilya Grigorik and Amit Handa clarified that browser actuation and structured protocols address complementary use cases: server-to-server UCP capabilities eliminate heavy browser overhead, respect merchant tone-of-voice and privacy constraints (e.g. cookie consent, regional compliance), and provide predictable semantic guarantees that conversational browser scrapers cannot replicate.
